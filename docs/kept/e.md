# E notes: Spotify playback adapter

- A trial feature, hidden unless the profile's `features.json` holds `{ "spotify": true }` (`desktop/features.js`). Without it the main process never starts the Spotify service and the preload exposes no `musicSpotify`, so Settings, search and playback show nothing of Spotify. Turn it on by creating that file in the profile folder (Settings > Show data folder) and relaunching. Spotify consent is set only by sign-in and sign-out; the catalog bridge refuses it from the window (`WINDOW_CONSENT_KEYS`). Known gap: turning the flag off after playing Spotify leaves those tracks in Recently Played and saved queues, where they cannot play and Next stops at them.
- Off until sign-in. Settings > Advanced has the section. Connect Spotify signs in with Kept's client ID: `SPOTIFY_CLIENT_ID` at launch, the repository variable `SPOTIFY_CLIENT_ID` baked in at build, or the one the regular Kept profile already used. Without one, or under "Use your own Spotify app", the user pastes their own (PKCE, no secret, loopback redirect `http://127.0.0.1:8888/callback`). In Spotify's development mode, only accounts on the app's allowlist can sign in. Needs Premium and a Spotify device (Connect). The Web Playback SDK is not used: it needs Widevine, which stock Electron lacks.
- `desktop/spotify.js` runs in the main process and handles PKCE sign-in, tokens encrypted with `safeStorage` (`spotify/tokens.bin`), the chosen device (`config.json`), device list, track search and the commands `play / pause / resume / seek`. The window gets a status and those commands over `musicSpotify` (preload), never a token or an API URL. Cancel and sign-out close any pending sign-in listener. Sign-out deletes the tokens and device, withdraws consent and drops in-flight responses. Kept leaves audio, artwork and the library on Spotify.
- Source: `SPOTIFY_SOURCE` in `shared/spotify-source.js`: kind `spotify`, evidence `deterministic`, licence `proprietary`, `analysisAllowed: false`, network `internet`, consent key `spotify` (new `ConsentKey`). Sign-in registers the source and records consent `granted`; sign-out records `denied`.
- The library search bar also searches Spotify tracks while signed in, online and not filtered to local music. Results form their own "On Spotify" section after the local groups. The request waits 400 ms for typing to settle and has its own owner, so local refreshes neither cancel nor repeat it. Development-mode apps get at most 10 results per search.
- `CatalogRef` kind `spotify` (id = Spotify track ID). The resolver resolves it synchronously to `{ kind: 'spotify-track', trackId }` when the ID is a plain Spotify ID. `Track.source` is `'spotify'`, `Track.id` is `spotify:track:<id>`, cover is empty. The queue and listening history retain the track reference, title, artist, album and duration after sign-out. Mixed queues replay through the resolver when signed in.
- `frontend/src/lib/spotify-adapter.ts` polls the remote position while Spotify owns playback. It reports track end, loss of device and foreign tracks. Polling normally runs once a second and waits longer when Spotify rate-limits requests or token refresh is temporarily unavailable.
- Refusals: `assertAnalysable` (`shared/source-policy.js`) is checked when a job of a class flagged `analysis: true` is queued or claimed in `LibraryWorker`. B1 must flag its analyse class and put `sourceId` in the payload. The tool runner refuses a Spotify ID as a seed or `similarTo`, never passes one to a feature store, and drops it from every result.
- Gaps: no Spotify library or playlists, only search. Sign-in, device choice, search and play/pause were run against a real Premium account on macOS. Not verified: Premium and allowlist errors, device handoff timing, token refresh in the wild, the connected and device-picker view of the Settings section (visual check covered the signed-out view at 1440x900 and 390x844).
