# B1 notes

The analyser turns each asset into an OpenL3 embedding plus the signal-processing vector, stores both in `features.sqlite`, and gives C1's tools a `FeatureSource` over it.

**Decoder.** `desktop/analysis/ffmpeg.js` resolves the bundled audio-only LGPL ffmpeg first (`desktop/bin`, or the app's resources when packaged). A system ffmpeg is used only in a development checkout; a packaged app never falls back. `scripts/build-ffmpeg.mjs` builds it from the pinned source and configure line in `shared/third-party.js`; `.github/workflows/ffmpeg.yml` builds and checks it per platform (not yet run in CI). Bounded excerpts only: 3 x 10 s per track.

**Model.** OpenL3 mel256, 6 windows per track (`openl3-mel256-w6`, B0: 78.6 % same album, 45 % same artist on another album). The ONNX file is not in git: `pnpm models` copies it from `KEPT_OPENL3_DIR` or exports it from the published weights. It runs on `onnxruntime-web` WASM in the `analyser` utility process (own process, nice 10). WASM uses one thread for the life of the process because ONNX Runtime fixes its thread pool at first initialization. The process exits after 60 s with nothing to do, which returns its memory.

**Distribution.** `pnpm models --strict` runs each ONNX graph on three synthetic log-mel inputs. Each pair of embeddings must differ by more than 0.1 RMS, and every component must be within `0.001 + 0.0001 × |reference|` of its reference in `desktop/scripts/openl3-reference.json`. The references and pinned ONNX hashes come from the measured B0 exports. A cached or supplied graph that passes the probes but lacks a matching hash is re-exported from verified weights for packaging. Development warns on fingerprint mismatches. The weights and mel basis must match their SHA-256 in both modes.

**Memory.** Session creation costs about 390 MB of RSS (75 MB before, 465 MB after) whatever the options. Tried: graph optimisation levels, no memory pattern, no CPU arena, model bytes used directly, no prepacking: all within 3 MB of each other. It is the WASM heap, which ORT never shrinks, so the only lever is the idle exit. Peak RSS of the analyser in the real app: 547 MB.

**Job class** (`desktop/analysis-jobs.js`). Class `analyse`, concurrency 1, priority below hashing, subject `method@version:asset`. A sweep walks the catalog's assets (`analysisCandidates`) after start and after each scan and queues what `features.sqlite` has no final outcome for. Policy `analysisAllowed = false` is refused three times: at the sweep (outcome `refused` recorded, earlier features removed), in `prepare` when the job is claimed, and in the handler. Tested with a source that forbids analysis. Unreadable files are recorded once; files not available now wait for the next sweep.

**Store** (`desktop/feature-store.js`, own worker thread). Tables `track_features`, `album_features` (mean over the album's analysed tracks), `analysis_outcomes`, `methods`, all keyed by method and method version. A new version recomputes; old rows are pruned. The file is regenerable: deleting or damaging it starts empty and the next sweep queues everything again. The DSP vector (loudness, dynamics, spectrum, onsets, tempo, key, 13 + 13 MFCC) is stored for all tracks; per the traits check only estimated energy ships (B2).

**FeatureSource** (`desktop/feature-source.js`) returns embeddings of the current method for album anchors and assets and is passed to `createToolRunner` in `desktop/main.js`. A refused asset has no row, so it never appears.

**Notices.** Settings, Licences tab, lists ffmpeg, onnxruntime-web, OpenL3 weights, Navidrome and Electron from `shared/third-party.js`.

**Measured** on an Apple Silicon laptop, real Electron app, temporary profile, a private real collection read only (958 tracks), the first album played through Kept's player (muted), next track every 25 s, 10 minutes. Hashing was done before. Playing policy as in A2.

| While playing, 10 min | |
| --- | --- |
| Tracks analysed | 77 (7.8 s per track, so about 2.1 h for the library) |
| `waiting` / `stalled` / error events | 0 / 0 / 0 |
| Audio clock gaps over 0.2 s | 0 |
| Renderer lag p95 / max | 2.6 / 27 ms |
| Main process lag p95 / max | 2.0 / 120 ms |
| Analyser peak RSS | 547 MB |

The whole-library time is extrapolated, not run: the idle phase of the harness crashed on a status read, and an interference with the window by another agent cost a first run. Idle speed in the app is therefore unmeasured (B0: 0.9 s of inference per track on two threads, plus decode, DSP and the job round trip). Untested: a slow or network disk, a phone, audible playback, a cold cache, Electron `utilityProcess` on Windows or Linux.

Open: the 120 ms main-process maximum was a single spike; packaged-app resolution of the ffmpeg and models is covered by unit tests only; the `ffmpeg` and packaging workflows have not run.
